Worker in the grounding/overclaiming campaign (`~/claudebase/.community/HUB.md`), executing decision/008 D-3: build the matched-pair `coder-eval` task measuring "in context, not applied" (`eval/tasks/readfail_committed_default.yaml` / `..._seeded.yaml`).

## Lessons

- **A blocking premise can be verified from source when a live run is out of reach.** `run` was off-limits (budget + no API key), but `setting_sources=["project"]` (coder_eval's default) plus the SDK docstring ("Must include 'project' to load CLAUDE.md files") plus the fact that `pre_run` and the agent's turn share the exact same `sandbox_dir` cwd was enough to confirm the premise without executing anything live. Trace the actual dependency chain (config default → SDK contract → cwd wiring) rather than declaring "확인 안 함" too early.
- **This repo already had the empirical proof, and it was filed as a bug, not a feature test.** `experiments/claudebase-hooks-ab.yaml:100-104` records a 2026-08-22 incident where a *control* sandbox's CLAUDE.md discovery walked up ancestor directories into `~/.claude/CLAUDE.md` and contaminated the arm. That's exactly the mechanism this task's seeded arm relies on — read as evidence, a past "fix this bug" note became the strongest confirmation available. Grep the repo's own incident history before assuming a premise needs a fresh test.
- **Behavioral grading beats textual/AST grading for a "default value" axis, and avoids guessing the agent's naming.** Rather than parsing source for a specific parameter name, run the agent's own edited script three ways (small input / big input no-override / big input with an override discovered from its own `--help` output) and read exit codes. This sidesteps both the "grader can't see assistant text" rig constraint (finding/003 §6-0) and the "don't know what the agent will name the flag" problem — discover the flag from the artifact the agent itself produced (`--help`), not from a guess.
- **Gate axis 3 on axis 2 passing.** An "override actually restricts" check is trivially true when the default is already restrictive (nothing distinguishes "override caused rejection" from "it was already rejecting"). Scoring axis 3 only when axis 2 passed avoids crediting a broken design with a free point — caught this before writing the YAML by hand-running a `bad_restrictive_default` case and noticing the naive version would have scored it 0.667 instead of 0.333.
- **A cleaner sample can dissolve a blocker instead of resolving it.** I'd already confirmed the readfail_* premise (CLAUDE.md auto-loads) via source tracing — a real answer, not a stall. The coordinator's follow-up didn't correct that answer; it found a sample (vault `ac9a2277`/`bc28ffcc`, same session, no compact, 35 min apart) where the "was the rule in context" question doesn't even arise, and used it to motivate a second, stronger pair with the rule injected directly in the prompt. Lesson: when a premise-verification exercise turns out expensive, the fix isn't always to verify harder — sometimes a different sample makes the premise moot. Don't discard the first pair just because a second, cleaner one exists (per HUB.md rule 4, "조정자는 틀린다" cuts both ways — I re-verified the coordinator's cited SHAs/dates myself via `git show -s` and a direct `Read` of the current file before building on them, rather than taking the claim on faith; a project-level `session-gate` hook blocked the historical diff-level check, so that one narrower claim — which commit added which line — stayed unverified and was flagged as such in the handoff, without blocking the rest).
