# Knowledge & Memory Lifecycle: Wiki, Remember, Learner/Skillify, Writer-Memory

OMC implements "compounding knowledge" as a set of four differently-shaped persistence surfaces plus a triage layer that routes knowledge between them: a markdown **wiki** (`.omc/wiki/`, Karpathy-style LLM knowledge base with append-merge semantics), the **notepad** (three-tier short-horizon memory in `.omc/notepad.md`), **project-memory** (auto-scanned structured facts in `.omc/project-memory.json`), and **learned skills** (flat markdown files with trigger frontmatter, auto-injected into future prompts). The `remember` skill is the human-facing router that decides which surface an item belongs to; `skillify` (with deprecated alias `learner`) is the promotion path that turns a session's hard-won workflow into a reusable skill file; `writer-memory` is a domain-specific memory system (fiction writing) built on a distinctive "reference implementation" pattern. The design intent, visible throughout the code, is capture-cheaply-then-curate: hooks write raw, bounded stubs automatically; an LLM pass with a quality gate promotes them; every store is plain markdown/JSON with no embeddings.

## What knowledge goes where

| Surface | Path | Shape | TTL / bound | Written by | Injected when |
|---|---|---|---|---|---|
| Wiki | `.omc/wiki/*.md` | md + YAML frontmatter, `[[links]]` | none; lint flags stale >30d (src/hooks/wiki/types.ts:180-184) | `wiki_ingest`/`wiki_add` MCP tools; SessionEnd auto-capture | SessionStart injects first 30 index lines (src/hooks/wiki/session-hooks.ts:91) |
| Notepad Priority Context | `.omc/notepad.md` `## Priority Context` | prose, max 500 chars | permanent until replaced | `notepad_write_priority`, `<remember priority>` tags | every SessionStart as `<notepad-context>` (scripts/session-start.mjs:992-1006) |
| Notepad Working Memory | `.omc/notepad.md` `## Working Memory` | timestamped entries | auto-pruned after `workingMemoryDays: 7` (src/hooks/notepad/index.ts:78-82) | `notepad_write_working`, `<remember>` tags | on demand via `notepad_read` |
| Notepad MANUAL | `.omc/notepad.md` `## MANUAL` | freeform | never pruned (src/hooks/notepad/index.ts:8,22) | user / `notepad_write_manual` | on demand |
| Project-memory | `.omc/project-memory.json` | typed JSON (`techStack`, `build`, `hotPaths`, `userDirectives`, `customNotes`) (src/hooks/project-memory/types.ts:6-18) | `customNotes` capped at 20 (src/hooks/project-memory/learner.ts:137-139) | PostToolUse learner + `project_memory_*` tools | SessionStart hook; also fed into wiki `environment.md` |
| Learned skills | `.omc/skills/*.md`, `~/.omc/skills/`, `~/.claude/skills/omc-learned/` | md with `name/description/triggers` frontmatter | none (config `storage.autoPrune` default false, `pruneDays: 90`) (src/hooks/learner/config.ts:56-59) | skillify workflow / `writeSkill()` | UserPromptSubmit trigger match (scripts/skill-injector.mjs) |
| Writer memory | `.writer-memory/memory.json` | single JSON document | manual backups to `backups/` | writer-memory skill (LLM executing reference lib) | skill invocation |

Persistence polarity is deliberate and opposite between the two durable stores: `ensureWikiDir` force-appends `wiki/` to `.omc/.gitignore` (wiki is project-local, never committed — src/hooks/wiki/storage.ts:54-64), while project-level learned skills at `.omc/skills/` are "Intended to be committed with the repo when you want the team to keep the skill" (skills/learner/SKILL.md:115).

## Wiki: append-merge knowledge base

Active wiring: 7 MCP tools (`wiki_ingest`, `wiki_query`, `wiki_lint`, `wiki_add`, `wiki_list`, `wiki_read`, `wiki_delete`) registered under `TOOL_CATEGORIES.WIKI` (src/mcp/tool-registry.ts:28,62); three lifecycle hook scripts wired in hooks/hooks.json — `wiki-session-start.mjs` (SessionStart, line 37), `wiki-pre-compact.mjs` (PreCompact, line 166), `wiki-session-end.mjs` (SessionEnd, line 211). The `/oh-my-claudecode:wiki` command is a thin dispatcher that tells Claude to read `skills/wiki/SKILL.md` and follow it (commands/wiki.md).

```
.omc/wiki/
├── index.md          reserved: auto-regenerated catalog, grouped by category
├── log.md            reserved: append-only operation chronicle
├── environment.md    reserved: auto-fed from project-memory.json
└── <slug>.md         knowledge pages (YAML frontmatter + markdown)
```

### Page format

Frontmatter schema (src/hooks/wiki/types.ts:17-36): `title`, `tags[]`, `created`, `updated`, `sources[]` (session IDs), `links[]` (slugs of `[[wiki-link]]` cross-references), `category`, `confidence: 'high'|'medium'|'low'`, `schemaVersion` (`WIKI_SCHEMA_VERSION = 1`, types.ts:14). Categories are a closed enum of 8: `architecture, decision, pattern, debugging, environment, session-log, reference, convention` (types.ts:39-47). `[[Page Name]]` links in content are extracted at ingest time, slugified, and stored in frontmatter `links` (src/hooks/wiki/ingest.ts:132-139) — lint later validates them. Slugs are `titleToSlug`: lowercase, non-alphanumeric runs to `-`, max 64 chars, with a deterministic hash fallback `page-<hex8>.md` for CJK/non-ASCII titles so they do not all collide on a hidden `.md` dotfile (src/hooks/wiki/storage.ts:390-409).

### Ingest = merge, never replace

`ingestKnowledge` is the single write path (wiki_add delegates to it after an already-exists guard that redirects the caller to `wiki_ingest` — src/tools/wiki-tools.ts:227-238). If the slug exists, it merges: tags/sources/links unioned, `confidence` keeps the higher rank, and content is **appended** as a timestamped section `\n\n---\n\n## Update (<ISO>)\n\n<content>` — existing prose is never rewritten (src/hooks/wiki/ingest.ts:99-129). Input is bounded at the tool schema: title ≤200 chars, content ≤50KB, ≤20 tags of ≤50 chars, ≤10 sources (src/tools/wiki-tools.ts:47-52). Every mutation runs inside `withWikiLock` — a wiki-wide sync file lock (`.wiki-lock`, `timeoutMs: 5_000, retryDelayMs: 50`, storage.ts:80-84) — then regenerates `index.md` and appends a `WikiLogEntry` (`timestamp`, `operation: 'ingest'|'query'|'lint'|'add'|'delete'`, `pagesAffected`, `summary`) to `log.md` (types.ts:64-73). Notably, even **queries and lints append to log.md** (query.ts:154-159, lint.ts:126-131), so the chronicle records reads as well as writes.

### Query: keyword scoring, no embeddings

"NO vector embeddings — query uses keyword + tag matching only" is a hard constraint (skills/wiki/SKILL.md:66). Tokenization handles CJK via character uni-grams plus bi-gram sliding windows alongside Latin word tokens (src/hooks/wiki/query.ts:28-61). Scoring is additive per page: +3 per matching filter tag, +2 per query term found in tags, +5 for full query in title (+2 per term otherwise), +1 per unique term in content with a ±40/+80-char snippet around the first hit; default `limit = 20` (query.ts:83-147). The tool description makes the division of labor explicit: "YOU synthesize answers with citations from the results — the tool returns raw matches only" (src/tools/wiki-tools.ts:98).

### Lint: six mechanical health checks

| Check | Type | Severity | Rule |
|---|---|---|---|
| Orphan | `orphan` | info | no incoming `links` from any other page (lint.ts:54-62) |
| Stale | `stale` | warning | `updated` older than `staleDays` (default 30, types.ts:182) |
| Broken ref | `broken-ref` | error | frontmatter `links` entry has no matching file (lint.ts:77-86) |
| Low confidence | `low-confidence` | info | `confidence: low` — "consider verifying or removing" (lint.ts:89-96) |
| Oversized | `oversized` | warning | content > `maxPageSize` (default 10_240 bytes) — "consider splitting" (lint.ts:99-108) |
| Structural contradiction | `structural-contradiction` | warning/info | pages sharing a 2-segment slug prefix with both `high` and `low` confidence, or same tag across different categories (lint.ts:143-188) |

Semantic contradiction detection is explicitly deferred: "requires LLM integration (v2)" (lint.ts:141). Lint reports; it never auto-fixes or deletes — repair is left to the LLM/human loop.

### Session lifecycle (capture-then-curate)

```
SessionStart ─ wiki-session-start.mjs ─→ lazy index rebuild if missing
                                       → feedProjectMemory(): project-memory.json newer than
                                         environment.md? regenerate environment.md (category:
                                         environment, confidence: high, sources:
                                         ["project-memory-auto-detect"])       (session-hooks.ts:195-262)
                                       → inject "[LLM Wiki: N pages at .omc/wiki/]" + first
                                         30 lines of index.md                  (session-hooks.ts:86-94)
PreCompact   ─ wiki-pre-compact.mjs   ─→ inject one-line survival summary
                                         "[Wiki: N pages | categories: ... | last updated: ...]"
SessionEnd   ─ wiki-session-end.mjs   ─→ if wiki.autoCapture (default true): write stub page
                                         session-log-YYYY-MM-DD-<sid8>.md (category: session-log,
                                         confidence: medium, tags: [session-log, auto-captured])
                                         whose body says "Review and promote significant findings
                                         to curated wiki pages via wiki_ingest" (session-hooks.ts:128-148)
```

SessionEnd auto-capture is deliberately dumb and bounded: "Does NOT do LLM-judged curation — that happens via skill on next session" (session-hooks.ts:104), hard 3s time budget checked inside the lock (session-hooks.ts:109,132), index rebuild skipped ("keep SessionEnd fast", :157), and it refuses to create the wiki dir just for logging (:120-123). All three hooks are fail-open: every handler is wrapped in try/catch returning `{}` or `{ continue: true }` ("Silently fail — session end should never block", :159-161). Config comes from `wiki` block of `.omc-config.json` (project `.omc/` first, then Claude config dir): `autoCapture: true, staleDays: 30, maxPageSize: 10_240` (types.ts:180-184).

### Guards

Reserved files `index.md`, `log.md`, `environment.md` are excluded from `listPages` and rejected by `writePageUnsafe` (storage.ts:36,263-266); `environment.md` gets its own dedicated writer `writeEnvironmentUnsafe` (storage.ts:350-353). `safeWikiPath` rejects `/`, `\`, `..` and re-resolves against the wiki dir to block traversal (storage.ts:188-198). All writes are `atomicWriteFileSync`. Frontmatter parsing normalizes CRLF and uses a deliberately tiny flat YAML parser (no nesting) with quoted-string unescaping (storage.ts:94-152).

## Remember: the triage skill and `<remember>` tags

`skills/remember/SKILL.md` is a pure prompt-side router with no code of its own. It names four destinations — project memory (durable team knowledge), notepad priority (short high-signal context), notepad working (temporary), and "Docs / AGENTS / CLAUDE files" — and prescribes a classify-then-place workflow: gather findings, classify each as durable fact / temporary note / operator preference / duplicate-stale-conflicting, propose a destination, write only there, and report conflicts (skills/remember/SKILL.md:13-28). Its rules encode the anti-dump philosophy verbatim: "Do not dump everything into one store", "If something is uncertain, mark it as uncertain rather than storing it as fact" (:31-35). The backing writes are the MCP tools `project_memory_read/write/add_note/add_directive` (src/tools/memory-tools.ts:32-220) and `notepad_read/write_priority/write_working/write_manual/prune/stats` (src/tools/notepad-tools.ts:38-315).

There is also a fully automatic runtime channel: when a delegation (Task) tool completes, `processRememberTags` scans the subagent's output — `<remember priority>content</remember>` goes to `setPriorityContext`, plain `<remember>content</remember>` to `addWorkingMemoryEntry` (src/hooks/omc-orchestrator/index.ts:322-343,471; duplicated in the wired PostToolUse script scripts/post-tool-verifier.mjs:715-741,1105). So subagents persist knowledge by emitting tags in prose, without tool access. Project-memory itself also learns passively on PostToolUse: hot-path tracking from Read/Edit/Write/Glob/Grep, build/test command detection from Bash, runtime-version and missing-dependency hints regexed out of tool output, and user-directive detection — each capped and behind both an in-process mutex and a cross-process file lock (src/hooks/project-memory/learner.ts:44-152).

## Learner/skillify: conversation into skill

This subsystem has two layers with different activity status.

**Prompt-side (active): skillify.** `/oh-my-claudecode:skillify` (aliases `[learner]`, skills/skillify/SKILL.md:3) instructs the LLM to extract a repeatable workflow into a skill draft. The quality gate is three questions, all must hold: "Could someone Google this in 5 minutes?" → No; "Is this specific to this codebase, project, or workflow?" → Yes; "Did this take real debugging, design, or operational effort to discover?" → Yes (skills/skillify/SKILL.md:17-21). The deprecated `skills/learner/SKILL.md` (kept "for internal implementation/history and compatibility", :9) carries the richer doctrine: skills are "principles and decision-making heuristics that teach Claude HOW TO THINK", not copy-paste snippets (:26-30); extraction is classified as **Expertise** (`{topic}-expertise.md`) vs **Workflow** (`{topic}-workflow.md`) so domain knowledge can evolve without destabilizing procedures (:104-110). It is a self-declared `level: 7` (self-improving) skill whose Expertise section may be rewritten by improvement cycles while the Workflow section stays frozen (:11-16). Output format is mandatory YAML frontmatter (`name`, `description`, `triggers[]`) — "Do **not** write plain markdown without frontmatter" (:119-132) — followed by a body template of `## The Insight / Why This Matters / Recognition Pattern / The Approach / Example` (:136-161). Storage: project `.omc/skills/<name>.md` (default) or user `${CLAUDE_CONFIG_DIR:-~/.claude}/skills/omc-learned/<name>.md` (:113-115); `omc-learned` is kept as a directory name only, never a public name (skillify SKILL.md:62).

**Code-side (mixed): `src/hooks/learner/`.** The programmatic writer `writeSkill()` validates via a numeric quality gate (start at 100; −30 problem <10 chars, −30 solution <20 chars, −20 no triggers, −10 oversize >`MAX_SKILL_CONTENT_LENGTH` 4000, −5 short triggers, −10 stopword triggers like `'the','a','this'`; pass requires no missing fields AND score ≥ `MIN_QUALITY_SCORE` 50 — src/hooks/learner/validator.ts:13-67, constants.ts). It emits `# Problem / # Solution` files with generated metadata (`id: skill-<ts36>-<rand4>`, `source: 'extracted'|'promoted'|'manual'`, `quality`, `usageCount: 0` — writer.ts:75-98), refuses to overwrite existing files, and flags duplicates when ≥50% of triggers overlap an existing skill (writer.ts:139-162). For user-scope skills it additionally creates a Claude Code native-format mirror `~/.claude/skills/<name>/SKILL.md` via symlink so the same file is discoverable by both loaders (writer.ts:116-118; src/utils/user-skill-compat.ts:14-60). `promotion.ts` promotes ralph-progress loop learnings (≥20 chars, keyword-extracted triggers, sorted by trigger specificity) into skills with `promoteLearning()` (promotion.ts:40-90). Config lives at `~/.claude/omc/learner.json`: `enabled: true`, `detection.promptThreshold: 60`, `promptCooldown: 5`, `quality.minScore: 50`, `storage.maxSkillsPerScope: 100`, `autoPrune: false`, `pruneDays: 90` (config.ts:44-62).

**Registration and injection (active).** Learned skills need no registry — registration IS the file. The wired UserPromptSubmit hook `scripts/skill-injector.mjs` (hooks/hooks.json:15-16) loads the esbuild bundle `dist/hooks/skill-bridge.cjs` (built from src/hooks/learner/bridge.ts, scripts/build-skill-bridge.mjs:12-20; inline fallback if unbuilt) and, per prompt: discovers skill files recursively (depth ≤10) from project dirs `.omc/skills/` and `.agents/skills/` (compat, read-only) then user dirs `~/.omc/skills/` and `~/.claude/skills/omc-learned/` — project outranks user (bridge.ts:384-455); matches prompt text against triggers, exact substring by default or Levenshtein-based fuzzy when frontmatter says `matching: fuzzy` (`fuzzyThreshold: 60`, bridge.ts:558-593), with Korean loanword transliteration expansion of English triggers (transliteration-map.ts:31-42); dedupes per session by content hash with a 1-hour session TTL and 30s metadata cache (bridge.ts:37-47); and injects at most 5 skills as a `<mnemosyne>` block of **compact descriptors, not bodies** — name, path, triggers, summary, and "If this skill is needed, read <path>" — under a hard 3000-char context budget with 1000-char per-descriptor cap (skill-injector.mjs:271-277,531-560,610-612). The TS library's own constant is `MAX_SKILLS_PER_SESSION = 10` (constants.ts) versus the active script's `5` — a live drift between library and hook.

**Vestigial (exported, not wired).** `detector.ts` (multilingual extractable-moment regexes in EN/ZH/KO/JA/ES with per-type confidences 60-80, trigger boost ≤15, prompt threshold 60) and `auto-learner.ts`/`auto-invoke.ts` (skill-worthiness scoring, invocation history) are re-exported through the learner barrel (src/hooks/learner/index.ts:22,27,29-38 — `auto-learner`'s `recordPattern` is deliberately renamed to `recordSkillPattern` to avoid a name collision with ralph's own `recordPattern`), which is in turn re-exported by the top-level hooks barrel (src/hooks/index.ts:564). But no wired hook script imports them; the only importers in the repo are unit tests (`src/__tests__/learner/auto-learner.test.ts`, `src/__tests__/mnemosyne/detector.test.ts`). Treat the fully-automatic extraction pipeline as designed-but-dormant: in practice extraction is human-invoked via skillify.

## Writer-memory: reference-implementation skill

`skills/writer-memory/` (level 7) is the most self-contained memory design: a fiction-writing memory with subcommands `init|char|rel|scene|query|validate|synopsis|status|export|backup` (SKILL.md:4,26-46). Its `lib/*.ts` files (memory-manager, character-tracker, relationship-graph, scene-organizer, synopsis-builder) are never compiled or imported by src/ — they are "a REFERENCE IMPLEMENTATION that Claude reads when the skill is activated. Written as real, runnable TypeScript with proper types, error handling, and atomic operations" (lib/memory-manager.ts:7-10). The LLM executes the semantics; the types are the spec. Data model: a single `.writer-memory/memory.json` document `WriterMemory { version: "1.0", project, characters: Record<string, Character>, world, relationships: Relationship[], scenes: Scene[], themes: Theme[], synopsis }` (memory-manager.ts:164-173), with Korean-first vocabulary as first-class fields — `speechLevel: "반말"|"존댓말"|"해체"|"혼합"`, character `taboo[]` (words the character would never say), `EmotionPoint` timelines with `intensity: 1..5`, relationship `evolution` event logs, scene `cuts[]` (memory-manager.ts:19-131). Two derived operations close the loop: `validate` checks proposed dialogue against speech level, tone, keywords, and taboo lists returning PASS/WARN/FAIL with suggested in-voice alternatives (SKILL.md:164-200), and `synopsis` regenerates a 5-element emotional summary (protagonist attitude, core relationship structure, emotional theme, genre-vs-real-emotion contrast, ending aftertaste — SKILL.md:139-162). Changes auto-backup to `.writer-memory/backups/` before modification; exports go to `exports/` (SKILL.md:222,410-418). Unlike the wiki, `.writer-memory/memory.json` is intended to be committed — "All data persists in `.writer-memory/memory.json` for git-friendly collaboration" (SKILL.md:22) — so its git polarity matches learned skills, not the self-gitignoring wiki. Wiring beyond the command dispatcher is limited to a `'writer-memory': 'medium'` risk-tier entry in the skill-state map (src/hooks/skill-state/index.ts:146; scripts/pre-tool-enforcer.mjs:1041).

## The compounding-knowledge philosophy, as implemented

Five commitments recur across all these subsystems. (1) **Plain text, no embeddings**: every store is markdown or JSON; search is keyword/tag scoring the LLM post-processes. (2) **Append, never destroy**: wiki ingest merges by appending timestamped sections; log.md only grows; notepad MANUAL is never pruned; learned-skill writes refuse to overwrite. (3) **Cheap automatic capture, gated promotion**: hooks write bounded stubs (session-log pages, hot paths, env hints, `<remember>` tags) with hard time/size budgets, and promotion to durable knowledge passes an explicit quality gate (skillify's three questions; validator score ≥50) executed by an LLM or human — the write path and the judgment path are separated. (4) **Self-description over registration**: a learned skill's frontmatter is its registration; discovery is directory scanning, injection is trigger matching, and injected context is descriptors-plus-paths rather than bodies, keeping the prompt budget flat as knowledge compounds. (5) **Fail-open everywhere**: every lifecycle hook swallows errors and returns `continue: true`; memory features degrade to no-ops (skill-injector falls back to inline implementation when the bridge bundle is missing) so knowledge machinery can never block real work.

## Patterns for sibling harnesses

- **Append-merge ingest keyed by title slug** (ingest.ts:99-129): same-title writes merge tags/sources and append a timestamped `## Update` section — knowledge accrues without loss. Adapt: this is exactly omx wiki's INV-2; add the confidence-max rule when merging.
- **Reserved-file trio (index/log/environment) with dedicated writers** (storage.ts:36,291-353): derived files are regenerated, never hand-edited, and rejected by the page writer. Adapt: any store with an auto-index should hard-reject index writes through the normal path.
- **Append-only operation chronicle that logs reads too** (query.ts:154-159): log.md records queries, giving a free usage signal for later gc/curation. Adapt: use query frequency to rank pages during lint/gc.
- **Mechanical lint + LLM repair split** (lint.ts): code detects orphans/stale/broken-refs/oversize/contradiction-shaped smells; the LLM decides fixes. Adapt: keep lint side-effect-free and severity-typed so a skill can consume the report.
- **Capture-then-curate SessionEnd stub** (session-hooks.ts:101-158): auto-write a bounded pointer page with an explicit "promote via ingest" instruction, under a 3s budget, never creating state dirs as a side effect. Adapt: any harness's session-end hook should write breadcrumbs, not conclusions.
- **Three-tier notepad (priority ≤500 chars / working 7d TTL / manual never-pruned)** plus `<remember>`/`<remember priority>` tags parsed from subagent prose (post-tool-verifier.mjs:715-741): lets tool-less subagents persist knowledge. Adapt: a single regex on worker output is enough to give every worker a memory API.
- **Quality-gate scoring before persisting a learning** (validator.ts:13-67): numeric penalties for vagueness (short problem/solution, generic triggers) with a hard pass threshold. Adapt: gate omp/oms `learn` promotions with the same start-at-100 penalty scheme.
- **Descriptor injection under a hard char budget** (skill-injector.mjs:276-277,545-560): inject name+triggers+path, instruct "read the file if needed". Adapt: any card/wiki injection should send pointers, not bodies, with an explicit omission marker when the budget truncates.
- **Frontmatter-as-registration for flat-file skills** with project>user precedence and content-hash session dedupe (bridge.ts:384-455): no registry file to drift. Adapt: reuse for omd/oms learned style cards.
- **Reference-implementation skill libs** (writer-memory lib/memory-manager.ts:7-10): ship typed, runnable-looking TS that the LLM reads as an executable spec instead of wiring a build. Adapt: cheap way to give a skill precise CRUD semantics without adding dist artifacts.
- **Slug hash fallback for non-ASCII titles** (storage.ts:397-406): prevents all CJK titles collapsing onto one hidden `.md` file. Adapt: mandatory for Korean-heavy harnesses.
- **Opposite git polarity per store**: wiki self-gitignores (storage.ts:54-64) while project learned skills are commit-intended. Adapt: decide and enforce polarity in code (auto-gitignore) rather than documentation.
