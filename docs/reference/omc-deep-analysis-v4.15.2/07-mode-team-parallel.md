# Parallel Orchestration: team, ultrawork, omc-teams (Worker Coordination)

OMC's parallel-execution territory spans three surfaces sharing one on-disk coordination substrate. `ultrawork` is a stateless prompt-level protocol ("fire independent Task() calls simultaneously"); `/team` is the full orchestration mode in which a lead session decomposes work, spawns N workers, and drives a staged plan/exec/verify/fix pipeline; `omc-teams` (`omc team ...` CLI) is the process-based runtime that launches real external CLI agents (claude/codex/gemini/antigravity/grok/cursor) in tmux panes, coordinated purely through files under `.omc/state/team/{teamName}/`. The file substrate — task files with lease-token claims, per-worker inbox/mailbox/heartbeat/status files, an append-only `events.jsonl` — is the load-bearing design: every worker, regardless of vendor, is coordinated by reading and writing JSON files via a single `omc team api` CLI, never by in-process RPC.

## Three surfaces at a glance

| Surface | Wiring | Worker type | State | Persistence |
|---|---|---|---|---|
| `ultrawork` | `skills/ultrawork/SKILL.md` (prompt only, no src/) | Claude `Task()` subagents | none ("no persistent state ... a component, not a standalone persistence mode", SKILL.md:132,9) | none — ralph layers persistence on top (SKILL.md:9,139-148) |
| `team` | `skills/team/SKILL.md` + `state_write(mode="team")` MCP state | Claude implicit-team teammates spawned via `Task(name="worker-N")` (SKILL.md:330-347) | `.omc/state/team-state.json` + `.omc/handoffs/<stage>.md` | staged pipeline, resume from `state_read(mode="team")` |
| `omc-teams` / `omc team` | `skills/omc-teams/SKILL.md`, `src/cli/commands/team.ts`, `src/team/runtime-v2.ts`, bundled `bridge/runtime-cli.cjs` (package.json `build:runtime-cli`) | external CLI processes in tmux panes | `.omc/state/team/{name}/**` file tree | job records + result artifacts; resumable via `resumeTeamV2` |

`ultrawork` is deliberately thin: routing guidance (haiku/sonnet/opus tiers), "never serialize independent work", `run_in_background: true` for >30s operations (skills/ultrawork/SKILL.md:30-40). It has no source module; everything below concerns team/omc-teams.

## Staged pipeline and lead/worker split (`/team` skill)

The canonical team runtime is a staged pipeline `team-plan -> team-prd -> team-exec -> team-verify -> team-fix (loop)` (skills/team/SKILL.md:99). Review is inserted structurally, not optionally: `team-verify` always runs `verifier`, escalating to `security-reviewer` for auth/crypto changes and `code-reviewer` (opus) for >20-file or architectural changes (SKILL.md:110,118). The user's `N:agent-type` only overrides the `team-exec` worker type; the lead picks specialists for every other stage (SKILL.md:115). `team-fix` is bounded by `max_fix_loops` (default 3, SKILL.md:260) and each completed stage must write a 10-20-line handoff to `.omc/handoffs/<stage-name>.md` (`Decided/Rejected/Risks/Files/Remaining`) so context survives lead compaction (SKILL.md:157-190). Watchdog policy at the skill level: status-check a task `in_progress` >5 min, presume worker dead at 10+ min silent, stop assigning to a worker after 2+ failed tasks (SKILL.md:381-383). The worker preamble forbids workers from spawning sub-agents, running tmux orchestration commands, or invoking `$team`/`$ultrawork`/`$autopilot`/`$ralph` (SKILL.md:469-476). Shutdown is a blocking request/response handshake: `shutdown_request` -> wait 30s per teammate for `shutdown_response` with echoed `request_id` (`shutdown-{timestamp}@{worker-name}`) -> only then clear state (SKILL.md:523-582).

## On-disk data model (the real schema)

All runtime state lives under the leader's cwd (typed builders in src/team/state-paths.ts:31-121):

```
.omc/state/team/{teamName}/
  config.json               # TeamConfig (workers, panes, resolved_routing, worktree_mode)
  manifest.json             # TeamManifestV2 (schema_version: 2, leader, governance)
  tasks/task-{id}.json      # TeamTask (+ .failure.json sidecar, .lock files)
  workers/{worker}/
    inbox.md                # lead -> worker instructions (append-only markdown)
    outbox.jsonl            # worker -> lead (legacy MCP-bridge lineage)
    heartbeat.json          # {pid,last_turn_at,turn_count,alive}
    status.json             # {state: idle|working|blocked|done|failed|draining, current_task_id}
    .ready                  # sentinel the worker touches on startup
    AGENTS.md               # worker protocol overlay
    identity.json / shutdown-request.json / shutdown-ack.json / verdict.json
  mailbox/{worker}.json     # peer-to-peer messages (+ .lock-{worker} lock dirs)
  dispatch/requests.json    # notification dispatch queue (+ .lock dir)
  events.jsonl              # append-only team event log
  monitor-snapshot.json     # previous monitor cycle for delta detection
  phase-state.json / .scaling-lock / watchdog-failed.json / startup-failure.json
.omc/team/{teamName}/worktrees/{worker}/   # git worktrees (note: NOT under state/)
```

Name/ID contracts (src/team/contracts.ts:1-15): `TEAM_NAME_SAFE_PATTERN /^[a-z0-9][a-z0-9-]{0,29}$/`, `WORKER_NAME_SAFE_PATTERN` (64 chars), `TASK_ID_SAFE_PATTERN /^\d{1,20}$/`. Task statuses are `pending | blocked | in_progress | completed | failed` with an intentionally minimal legal-transition table — only `in_progress -> completed|failed` (contracts.ts:9-15); claims, not transitions, move tasks out of `pending`.

The v2 task record (`TeamTask`/`TeamTaskV2`, src/team/types.ts:195-213) carries `id, subject, description, status, role?, owner?, result?, error?, blocked_by?/depends_on?, version, claim?, created_at, completed_at?` plus optional `delegation` plan and `delegation_compliance` evidence. `TeamConfig` (types.ts:301-331) persists `tmux_session`, `leader_pane_id`, per-worker `WorkerInfo` (`pane_id`, `worker_cli`, `worktree_path/branch`, `output_file` for verdict roles), and the immutable `resolved_routing` snapshot. Worker caps: `DEFAULT_MAX_WORKERS = 20`, `ABSOLUTE_MAX_WORKERS = 20` (types.ts:538-539); CLI accepts 1-20 workers (`MAX_WORKER_COUNT = 20`, src/cli/commands/team.ts:28-29), the omc-teams skill recommends 1-10 (skills/omc-teams/SKILL.md:27).

## Atomic claiming: two generations

**Generation 1 (lock-file claim, src/team/task-file-ops.ts).** `acquireTaskLock` creates `{taskId}.lock` with `O_CREAT|O_EXCL|O_WRONLY` — "the kernel guarantees no two openers succeed" (task-file-ops.ts:63). Lock payload is `{pid, workerName, timestamp}`; a lock is stale when older than `DEFAULT_STALE_LOCK_MS = 30_000` AND the owning PID is dead, in which case it is reaped and retried once (task-file-ops.ts:38,119-138). `findNextTask` does a lock-free pre-check (owner match + `status === 'pending'` + blockers resolved), acquires the lock, re-reads under lock, then stamps `claimedBy/claimedAt/claimPid` and `status: 'in_progress'` (task-file-ops.ts:286-341). Failure sidecars (`{taskId}.failure.json`) count retries; `DEFAULT_MAX_TASK_RETRIES = 5` (task-file-ops.ts:384).

**Generation 2 (lease + optimistic version, src/team/state/tasks.ts — the active v2 path behind `omc team api claim-task`).** `claimTask` verifies the worker exists in config, checks dependency readiness twice (before and after lock), rejects if `expected_version` mismatches, then writes `claim: { owner, token: randomUUID(), leased_until: now + 15min }` and `version + 1` (state/tasks.ts:88-95). `transitionTaskStatus` demands the exact `claim_token`, an unexpired (`leased_until > now`) lease, and the declared `from` state (rejecting with `claim_conflict`, `lease_expired`, or `invalid_transition`); on `completed` it persists the passed `result` and clears `claim`, and for tasks whose `delegation` plan has mode `auto|required` (or `required_parallel_probe === true`) it rejects with `missing_delegation_compliance_evidence` unless the result contains a literal `Subagent spawn evidence:` or `Subagent skip reason:` line (state/tasks.ts:172-197, 105-134) — a text-protocol compliance gate parsed by case-insensitive multiline regex. `releaseTaskClaim` is the explicit rollback path back to `pending`.

## Worker spawn and lifecycle (runtime v2, default-on)

Runtime v2 is enabled unless `OMC_RUNTIME_V2` is `0|false|no|off` (src/team/runtime-flags.ts:6-11). `startTeamV2` (src/team/runtime-v2.ts:961-1466) proceeds: (1) sanitize/validate team name; (2) resolve the role-routing snapshot once via `buildResolvedRoutingSnapshot()` — immutable for the team's lifetime, "config edits mid-lifetime do NOT change routing" (runtime-v2.ts:966-969); (3) preflight-resolve absolute CLI binary paths per provider, rewriting headless-unsupported providers to Claude and emitting a loud `cli_binary_missing:{agent}` team event on fallback (runtime-v2.ts:1005-1071); (4) write `tasks/task-{i}.json` files; (5) create per-worker git worktrees when enabled; (6) write each worker's `AGENTS.md` overlay; (7) create the tmux session (leader pane), then for each initial allocation split a pane, launch the CLI with env `OMC_TEAM_STATE_ROOT`, `OMC_TEAM_LEADER_CWD`, `OMC_TEAM_WORKTREE_PATH`, `OMC_TEAM_WORKER_CWD` (runtime-v2.ts:696-702), and dispatch the startup instruction.

The startup instruction (`buildV2TaskInstruction`, runtime-v2.ts:477-519) is a numbered contract: claim via `omc team api claim-task ... --json`, save `claim_token`, do the work, transition via `transition-task-status`, "Do NOT write done.json or edit task files directly". The worker overlay (src/team/worker-bootstrap.ts:166-265) adds: FIRST ACTION `touch .../.ready` sentinel; startup ACK message to `leader-fixed`; heartbeat/status file formats; the state-root resolution order (`OMC_TEAM_STATE_ROOT` env -> identity -> config -> `{cwd}/.omc/state/team/{team}`); shutdown-ack format `{"status":"accept"|"reject","reason":...,"updated_at":...}`; and hard rules — never spawn sub-agents, never create tmux panes, worker control surface is only `omc team api ... --json`.

Dispatch distinguishes interactive agents (claude/codex: wait for pane readiness, then tmux `send-keys` a one-line trigger "Read {inbox.md}, execute now, report concrete progress") from prompt-mode agents (gemini/antigravity: full instruction stays in `inbox.md`, only a short file-pointer prompt is passed as CLI args "to avoid echoing reviewer/seed prompt text into tmux scrollback", runtime-v2.ts:747-751). Spawn then blocks on *startup evidence* — task claim visible in the task file or worker status progress — and for Claude workers retries the Enter key up to 4 times because "Claude Code v2.1.x sometimes swallows the Enter key sent immediately after a fresh pane reports ready" (runtime-v2.ts:831-867). Any failure yields a `startup_manual_intervention_required:{worker}:{reason}` event rather than silent loss; startup errors before config persists trigger full rollback with a `startup-failure.json` marker (runtime-v2.ts:893-949).

## Monitoring, dead workers, stale tasks

The detached runner (`bridge/runtime-cli.cjs`, src/team/runtime-cli.ts) reads a JSON config from stdin, starts the team, and polls `monitorTeamV2` every `pollIntervalMs` (default 5000). Each cycle produces a `TeamSnapshotV2` (runtime-v2.ts:1787-1999): pane liveness per worker, status/heartbeat freshness (`MONITOR_SIGNAL_STALE_MS = 30_000`), task counts, inferred phase, and *stall diagnosis* — a pane that looks idle at a prompt is classified as `missing_dependency`, `no_work_start_evidence`, `stale_or_missing_worker_reports`, or `no_meaningful_turn_progress` (>5 turns without progress), each generating an "Investigate {worker}..." recommendation (runtime-v2.ts:1894-1918). Phase is inferred purely from task-status distribution (`inferPhase`, src/team/phase-controller.ts:34-98), with the subtle rule that tasks marked `completed` but carrying `metadata.permanentlyFailed === true` count as failed.

Failure machinery, layered:

| Guard | Mechanism | Evidence |
|---|---|---|
| Dead worker requeue | in_progress tasks of dead workers get a `worker_dead:{owner}` failure sidecar and are reset to `pending` under a file lock ("only requeue if still in_progress") | runtime-v2.ts:1534-1594 |
| Circuit breaker | 3 consecutive monitor failures -> write `watchdog-failed.json` (`CIRCUIT_BREAKER_THRESHOLD = 3`) | runtime-v2.ts:1472-1524 |
| Task-count mismatch | observed != expected task count for 2 consecutive polls -> fail fast (`mismatchStreak >= 2`) | runtime-cli.ts:548-559 |
| All-dead heuristic | all worker panes dead + outstanding work -> team failed | runtime-cli.ts:599-605 |
| Sentinel gate | before declaring success, `waitForSentinelReadiness` runs the factcheck sentinel (default timeout 30_000ms, poll 250ms); blockers veto completion | runtime-cli.ts:572-590, src/team/sentinel-gate.ts |
| Idle nudge | idle pane (prompt visible, no active task) for 30s gets tmux-typed "Continue working on your assigned task and report concrete progress (not ACK-only)", max 3 nudges | src/team/idle-nudge.ts:29-33 |
| v1 watchdog (legacy) | 1000ms tick scanning per-worker `done.json`; dead pane or 3 unresponsive ticks (`UNRESPONSIVE_KILL_THRESHOLD = 3`) -> kill + requeue | src/team/runtime.ts:455,545-651 |

Terminal success intentionally does NOT tear down: `exitWithoutShutdown` prints "preserving team state for inspection. Run \"omc team shutdown {team}\" when explicit cleanup is desired" (runtime-cli.ts:166-179). `shutdownTeamV2` (runtime-v2.ts:2013-2272) enforces a shutdown gate (`allowed` only when pending=blocked=in_progress=failed=0, unless `--force`, a governance override, or ralph's failure-only bypass), writes shutdown requests + inbox notes, waits `timeoutMs` (default 15_000) for `shutdown-ack.json` per worker (a `reject` aborts non-forced shutdown), kills panes, and — critically — *preserves* worktrees and state whenever pane liveness is `alive` or `unknown`, or worktrees are dirty ("cleanup never force-removes dirty worker changes", src/team/git-worktree.ts:11-13).

## Communication channels

Four distinct channels, all file-backed: (1) **inbox.md** — leader-to-worker instruction stream, appended with `---` separators (worker-bootstrap.ts:293-305); (2) **mailbox** — peer-addressable JSON messages `{message_id, from_worker, to_worker, body, created_at, notified_at?, delivered_at?}` written under a per-recipient lock dir, each send appending a `message_received` event (src/team/team-ops.ts:575-602); broadcast is just a fan-out of sends skipping the sender; (3) **dispatch queue** — `dispatch/requests.json` records every notification attempt with `transport_preference` (`hook_preferred_with_fallback | transport_direct | prompt_stdin`) and status (`pending -> notified -> delivered | failed`), locked via `O_EXCL` mkdir (src/team/dispatch-queue.ts:1-12); the notifier fallback chain is hook -> tmux `send-keys` -> mailbox-persisted (src/team/mcp-comm.ts); (4) **events.jsonl** — append-only event log (`task_completed`, `task_failed`, `worker_idle`, `worker_stopped`, `message_received`, `shutdown_ack`, `shutdown_gate`, `shutdown_gate_forced`, `approval_decision`, `team_leader_nudge`; contracts.ts:25-36) written with O_APPEND (src/team/events.ts:22-40). The leader itself has an inbox (`leader-fixed` is the leader's fixed worker id) used by the merge orchestrator for conflict pages only, "not on every merge success" (src/team/merge-orchestrator.ts:40-45). Governance defaults: `delegation_only: false, plan_approval_required: false, nested_teams_allowed: false, one_team_per_leader_session: true, cleanup_requires_all_workers_inactive: true` (src/team/governance.ts:18-24); `assertTeamSpawnAllowed` blocks a worker (detected via `OMC_TEAM_WORKER` env identity) from starting nested teams unless the parent manifest allows it (src/cli/team.ts:155-176).

## Role routing and review insertion (Option E)

Per-role provider/model routing is declared in `team.roleRouting` (`.claude/omc.jsonc` project > `~/.config/claude-omc/config.jsonc` user, both overridden by env `OMC_TEAM_ROLE_OVERRIDES` JSON; invalid env JSON logs a warning and is ignored — skills/team/SKILL.md:948-951). Fifteen canonical roles map to default tiers (`orchestrator/planner/analyst/architect/critic/code-reviewer/code-simplifier` = HIGH; `executor/debugger/security-reviewer/test-engineer/designer/document-specialist` = MEDIUM; `writer/explore` = LOW; src/team/stage-router.ts:51-67). `resolveTaskAssignment` resolves per task: explicit `task.role` -> alias normalization -> snapshot lookup; else `routeTaskToRole` infers a lane intent (`implementation | verification | review | debug | design | docs | build-fix | cleanup`) from regex keyword tables over the task text (src/team/role-router.ts:10-60); else round-robin fallback agent (runtime-v2.ts:278-296).

Reviewer roles routed to external CLIs get the **verdict-file contract** (AC-7): for `CONTRACT_ROLES = {critic, code-reviewer, security-reviewer, test-engineer}` on codex/gemini/grok (never claude or cursor — cursor is an interactive REPL that "cannot perform the write-verdict-and-exit dance", src/team/cli-worker-contract.ts:22-69), the prompt instructs writing strict JSON `{role, task_id, verdict: approve|revise|reject, summary, findings: [{severity: critical|major|minor|nit, message, file?, line?}]}` to `workers/{worker}/verdict.json`. The monitor's `processCliWorkerVerdicts` post-exit handler parses it, writes the terminal task status (approve -> completed, revise/reject -> failed) directly — the worker process is gone and cannot re-enter the claim protocol — and renames the file `verdict.processed.json` to prevent reprocessing (runtime-v2.ts:1617-1633). Cursor workers are hard-restricted to executor-style tasks by regex intent guards (runtime-v2.ts:122-139).

## Worktree isolation and auto-merge

Worktrees are opt-in via `OMC_TEAM_WORKTREE_MODE` or `team.ops.worktreeMode`: `disabled | detached | named` (`branch`/`named-branch` normalize to `named`; `1/true/yes/on/enabled` normalize to `detached`; src/team/git-worktree.ts:441-448). Worker worktrees live at `{repoRoot}/.omc/team/{team}/worktrees/{worker}` on branch `omc-team/{teamName}/{workerName}` (git-worktree.ts:88-95). `ensureWorkerWorktree` requires a clean leader tree (`leader_worktree_dirty` error, ignoring untracked `.omc/`), reuses compatible clean worktrees, and throws rather than deletes on dirty/mismatched ones (git-worktree.ts:110-121,454-520). Each worktree root gets the worker overlay installed as `AGENTS.md` with a backup for restore (`installWorktreeRootAgents`).

`--auto-merge` (equivalent `OMC_TEAMS_AUTO_MERGE=1`, v2-only, refuses `main`/`master` leader branch, forces `named` mode; runtime-v2.ts:979-992) starts the merge orchestrator (src/team/merge-orchestrator.ts): a commit watcher per registered worker branch; on SHA change it merges from a dedicated "merger" worktree into the leader branch, mutex-serialized, then fans out auto-rebase to every other worker with a `.hook-paused` sentinel to pause commit-cadence hooks during rebase, dirty-tree audit on resolution, persisted last-SHA state for restart recovery (`recoverFromRestart`), and drain-on-stop with a teardown audit of unmerged workers. Orchestrator events go to a dedicated `orchestrator-events.jsonl`, deliberately not the shared `events.jsonl` (merge-orchestrator.ts:32-38). Worker commits are induced by `installCommitCadence` git-hook installation with a fallback poller (runtime-v2.ts:754-767). Auto-merge startup failure is fatal by design: "continuing would leave users believing worker edits are being merged when they are not" (runtime-v2.ts:1401-1455).

## Scaling, jobs, and the CLI surface

Dynamic scaling is gated by `OMC_TEAM_SCALING_ENABLED` (src/team/scaling.ts:60-66): `scaleUp` adds panes under a file-based `.scaling-lock` with a monotonic `next_worker_index` so names never collide across scale events; `scaleDown` sets targets to `'draining'` status, waits `drainTimeoutMs` (default 30_000) for current tasks to finish, then kills panes and cleans worktrees (scaling.ts:521-615).

`omc team [N:agent[:role]] "task"` (src/cli/commands/team.ts) parses count (1-20), providers (`claude|codex|gemini|grok|cursor|antigravity`), and optional role; heuristically decomposes the task string into subtasks by numbered lines, bullets, or conjunction splitting unless `--no-decompose`/`--fixed-workers` is given or the text carries atomic signals (>=3 file refs or backticked symbols, or explicit "parallel/concurrently" keywords) (commands/team.ts:160-240). The launcher then spawns `bridge/runtime-cli.cjs` as a **detached** node process with `OMC_JOB_ID`/`OMC_JOBS_DIR` env (jobs dir defaults to the global state path `team-jobs`; job ids match `/^omc-[a-z0-9]{1,16}$/`), piping the config JSON to stdin (src/cli/team.ts:191,379-429). The runner writes `{jobId}.json`, `{jobId}-panes.json` (pane IDs for later cleanup), and `{jobId}-result.json` artifacts; `omc team status|wait|shutdown|cleanup|resume` operate on these. Terse worker finals ("Done.", "OK") are substituted with the newest `outputs/team-{team}-task-{id}-*.md` content capped at 2000 chars (runtime-cli.ts:199-269). Multiplexer detection: real tmux is reused when `$TMUX` is set; `CMUX_SURFACE_ID` without `$TMUX` produces native cmux splits; a plain terminal gets a detached tmux session (skills/omc-teams/SKILL.md:57-66; src/team/tmux-session.ts:28-45). Windows is supported through psmux's tmux-compatible binary (skills/team/SKILL.md:198-207).

## Patterns for sibling harnesses

- **File-tree as the coordination bus.** Every worker, regardless of vendor CLI, coordinates through JSON files under one state root, mutated only via a small CLI API — no sockets, no shared memory. Adaptation: give each harness a `.om*/state/<unit>/` tree plus one `<harness> api` verb set; vendor-agnostic workers come free.
- **Claim = lease token + optimistic version, transition = token-gated state machine.** `claim-task` issues a UUID token with a 15-min lease and bumps `version`; terminal transitions require the exact token, unexpired lease, and declared `from` state. Adaptation: this single pattern eliminates lost-update races for any multi-writer artifact, not just tasks.
- **O_EXCL lock files with PID-aware stale reaping.** Locks older than 30s whose owner PID is dead are reaped and retried once. Adaptation: standard recipe for cross-process critical sections on plain filesystems.
- **Evidence-gated spawn.** Do not trust "I sent the prompt"; block until the worker produces observable evidence (claim visible in the task file, status progress, `.ready` sentinel), and retry the Enter keystroke against TUI input races. Adaptation: any harness driving TUIs via send-keys needs an evidence loop, not a sleep.
- **Requeue-not-retry for dead workers.** Reset a dead owner's in_progress tasks to `pending` under lock with a failure sidecar counting retries (budget 5), letting any surviving worker claim them. Adaptation: separates "task failed" from "worker died" cleanly.
- **Compliance by parseable result text.** Completion evidence (`Subagent skip reason:` / `Subagent spawn evidence:`) is enforced by regex over the required `result` field. Adaptation: cheap way to make policy machine-checkable when workers are LLMs that can only emit text.
- **Verdict-file contract for reviewers that cannot call your API.** Reviewer-role external workers write strict JSON `{verdict, summary, findings[]}` to a pre-agreed path; the monitor converts it into task transitions post-exit and renames it `.processed`. Adaptation: works for any one-shot judge process (linters, external LLM CLIs).
- **Immutable resolved-routing snapshot.** Resolve role -> provider/model once at creation, persist in config, and have spawn/scale/restart read the snapshot. Adaptation: prevents mid-run config drift from producing heterogeneous reruns.
- **Preserve-on-doubt teardown.** Cleanup runs only when pane death is proven and worktrees are clean; otherwise state is preserved with a stderr notice, and success exits deliberately keep state for inspection. Adaptation: default to forensic preservation, make destruction the explicit command.
