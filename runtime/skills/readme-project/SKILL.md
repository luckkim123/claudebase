# Generating Professional README

## Overview

Analyze a project's codebase and generate a README.md that matches the quality standard of top-tier open-source projects (Google, Meta, Microsoft, Vercel, etc.). The core principle: **scanability over completeness** -- readers scan in 10 seconds, then decide to read deeper.

## When to Use

- User provides a folder path and asks for a README
- User asks to rewrite or improve an existing README
- User asks for a "professional" or "production-quality" README

## When NOT to Use

- Internal/private repos that won't be shared — the OSS-style hero block, badges, and "scanability over completeness" framing assume an external audience.
- Single-script or one-file projects — a docstring or the top comment is the right scale; a multi-section README is overkill.
- Project types with their own dedicated README skill (e.g. an `oh-my-claudecode` plugin README) — defer to the more specific skill if one applies.
- When the user explicitly wants a tutorial, walkthrough, or design doc — this skill produces a reference-style README, not narrative documentation. Suggest a different artifact.

## Phase 1: Project Analysis

Scan these files to understand the project. Use parallel tool calls for speed.

**Identity files** (what is this project?):
- `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `setup.py`, `setup.cfg`
- `README.md` (existing), `CHANGELOG.md`, `CONTRIBUTING.md`
- `.github/workflows/*.yml` (CI setup)

**Structure files** (how is it organized?):
- Top-level directory listing
- `src/` or `source/` or `lib/` structure (1 level deep)
- Test directory structure

**Dependency files** (what does it use?):
- Lock files: `package-lock.json`, `poetry.lock`, `Cargo.lock`, `go.sum`
- Requirements: `requirements*.txt`, `environment.yml`

**Config files** (code quality & tooling):
- Linter/formatter config: `.eslintrc`, `ruff` section in pyproject.toml, `rustfmt.toml`
- Type checker config: `tsconfig.json`, pyright/mypy sections
- Docker: `Dockerfile`, `docker-compose.yml`

**Extract from analysis:**
- Project name, version, license type
- Primary language and framework
- Key dependencies (top 5-8)
- Available scripts/commands
- Supported platforms
- CI/CD status badge URLs
- Documentation URL (if exists)

## Phase 2: Generate README

Follow this template strictly. Every section has constraints.

```markdown
<div align="center">

# Project Name

**One-line tagline that says what it does and why it matters.**

[![Badge1][badge1-img]][badge1-url]
[![Badge2][badge2-img]][badge2-url]
[![Badge3][badge3-img]][badge3-url]

[Documentation][docs-url] | [Getting Started](#getting-started) | [Contributing](#contributing)

</div>

## Overview

1-3 paragraphs: What is it? What problem does it solve? Who is it for?
Focus on VALUE, not implementation details.

## Key Features

- **Bold Keyword**: One-line explanation of the benefit

## Getting Started

### Prerequisites

Bullet list of requirements.

### Installation

Primary method first (one-liner).

### Quick Start

5-15 line RUNNABLE code example.

## Usage

<details>
<summary><strong>Advanced Usage</strong></summary>
Progressive examples from simple to complex.
</details>

## Documentation

Link to hosted docs. 1-3 lines max.

## Project Structure

Top-level only. MAX 15 lines.

## Contributing

1-2 sentence invitation + link to CONTRIBUTING.md.

## License

License name + link. 1-2 lines max.

[badge1-img]: https://img.shields.io/...
[badge1-url]: https://...
[docs-url]: https://...
```

## Section Constraints

| Section | Max Lines | Must Include | Must NOT Include |
|---|---|---|---|
| Hero Block | 15 | Centered title, tagline, 3-6 badges, nav links | Paragraph text, images |
| Overview | 3-8 lines | Value proposition, target audience | Implementation details |
| Key Features | 3-6 bullets (prefer 4-5) | Bold keyword + benefit | Sub-bullets, code blocks, 7+ items |
| Prerequisites | 3-5 bullets | Language version, OS | Obvious items |
| Installation | 5-10 lines | Primary install command | Multiple alternatives upfront |
| Quick Start | 5-15 code lines | Runnable example | Imports-only or pseudo-code |
| Project Structure | 10-15 lines | Top-level dirs only | Nested file listings |
| Contributing | 3-5 lines | Link to CONTRIBUTING.md | Full guidelines inline |
| License | 1-2 lines | License name + link | Legal text |

## Badge Selection

Pick 3-6: Package version, CI status, License, Language version, Downloads, Community.
Use shields.io default flat style. Center-align all badges.

## Progressive Disclosure Rules

Wrap in `<details>` tags: Alternative install methods, Advanced usage, Config reference, Full structure, FAQ.
Keep visible: Hero block, Overview, Key Features, Installation, Quick Start, Contributing, License.

## Adaptation by Project Type

**Library/SDK**: Emphasize Installation, Quick Start code, API examples
**Application**: Emphasize Screenshots/demo, system requirements, configuration
**Framework**: Emphasize Architecture overview, extension points, ecosystem
**CLI Tool**: Emphasize Install one-liner, command examples, flags table

## Quality Checks

- [ ] Hero block centered, tagline is ONE sentence
- [ ] Badges: 3-6 count, centered, version badge first
- [ ] Features: 3-6 bold-keyword bullets
- [ ] Quick Start has a RUNNABLE code block
- [ ] No section exceeds its max line constraint
- [ ] Advanced content in `<details>` tags
- [ ] Reference-style links at bottom
- [ ] No AI attribution
- [ ] All links are real

## Common Mistakes

| Mistake | Fix |
|---|---|
| Listing 10+ features | Pick the 3-6 most differentiating ones |
| Full directory tree | Top-level only, link to docs |
| Installation before explanation | "What & Why" before "How" |
| Placeholder URLs | Only include real links |
| All content visible | Wrap advanced sections in `<details>` |
| Left-aligned everything | Center the hero block |
| Inline URLs in prose | Use reference-style links at bottom |
